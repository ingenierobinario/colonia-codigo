Casi todos los problemas se reducen a tres preguntas: ¿el core está corriendo?, ¿este cliente llega a él?, ¿lo deja
entrar? Empieza por ahí.

## ¿El core está corriendo, y con qué código?

`colonia status` le pregunta al core mismo. La primera línea es la versión y el commit que corre (`code_sha`), y después
vienen cuánto lleva prendido, la memoria, la URL y el estado de cada subsistema:

```bash
colonia status          # versión y code_sha del core, subsistemas, equipo, dispositivos, acceso
colonia --version       # la versión y el commit de esta CLI, sin preguntarle al core
colonia service status  # ¿el servicio está instalado, y el core responde?
```

Si el commit no es el que esperas (por ejemplo, después de actualizar), el core sigue corriendo el código viejo:
reinícialo con `colonia service restart`, o cierra y abre la app de escritorio. En el panel, **Configuración › Avanzado**
muestra la misma versión y el `code_sha`.

Si el core no está corriendo, vas a ver:

<Terminal command="colonia status">{`colonia: Core not running: See why and what to do: colonia doctor`}</Terminal>

`colonia doctor` revisa este ordenador sin el core: qué dice el log del core sobre su último arranque, si el servicio
está instalado y corriendo, y si salió un Colonia más nuevo. Termina con el comando a correr. Si una versión no puede
arrancar (su log muestra `ERR_MODULE_NOT_FOUND`), `colonia update` la reemplaza aunque el core esté caído, en un Colonia
instalado con el script de instalación; la app de escritorio se reemplaza bajando la más nueva.

Si no, arráncalo con la app de escritorio, con `colonia service install` (o `colonia service restart` si el servicio ya
existe), o con `pnpm dev` desde el código. Si arranca y se cae, lee su log.

## Dónde están los logs

Corra como corra Colonia (la app de escritorio, el servicio o `pnpm dev`), el core escribe su log en el mismo archivo,
en la carpeta `logs` de su home. Una línea JSON por evento; las credenciales que aparezcan se reemplazan por
`[redacted]`.

| Sistema | El log del core |
|---|---|
| macOS | `~/.colonia/v2/logs/core.log` (`/Users/<tú>/.colonia/v2/logs/core.log`) |
| Linux | `~/.colonia/v2/logs/core.log` (el servicio además lo manda a `journalctl --user -u colonia -f`) |
| Windows | `%USERPROFILE%\.colonia\v2\logs\core.log` |

Si definiste `COLONIA_HOME`, es `<COLONIA_HOME>/logs/core.log`. Cuando el archivo pasa los 20 MB, el core guarda el viejo
como `core.log.1` y empieza uno nuevo.

Tres formas de leerlo:

- En el panel: **Configuración › Registros** muestra las líneas más nuevas primero, con filtro por nivel, búsqueda y
  la ruta del archivo para copiar.
- `colonia logs` le pregunta al core (sirve también para un core en un servidor), con `-n 200`, `--level error`,
  `--grep texto` o `--json`. Si ningún core responde, lee el archivo de este ordenador.
- `colonia service logs -f` lee el archivo de este ordenador y lo sigue.

<Terminal command="colonia logs --level error -n 2">{`# ~/.colonia/v2/logs/core.log
2026-10-15 09:12:03  ERROR  core  channel stopped  {"channel":"acme"}
2026-10-15 09:14:47  ERROR  output  TypeError: Cannot read properties of undefined`}</Terminal>

Las líneas del origen **Salida del proceso** son lo que el core imprimió fuera de su log, como la traza de una caída.

Las versiones de la app de escritorio anteriores a este cambio escribían `core.log` en la carpeta de logs de la app
(`~/Library/Logs/Colonia` en macOS, `%APPDATA%\Colonia\logs` en Windows, `~/.config/Colonia/logs` en Linux); las líneas
viejas siguen ahí.

## Una actualización de la app no se instala

Si **Reiniciar ahora** no puede poner la versión nueva, la ventana de actualización dice por qué, o después de un
minuto avisa que Colonia no se reinició. Sal de Colonia (Cmd+Q en macOS, **Salir de Colonia** desde el icono de la bandeja en los
demás) y vuelve a abrirlo. En macOS y Linux, una versión ya descargada se instala cuando Colonia se cierra; en Windows,
elige **Reiniciar ahora** otra vez cuando esté abierto. Si Colonia no se cierra, fuerza la salida (Monitor de Actividad en
macOS, Administrador de tareas en Windows).

La app de escritorio anota cada paso de su propia actualización (descarga, reinicio, salida y, en macOS, el cambio de
`Colonia.app`) en `update.log`, dentro de su carpeta de logs: `~/Library/Logs/Colonia/update.log` en macOS,
`%APPDATA%\Colonia\logs\update.log` en Windows, `~/.config/Colonia/logs/update.log` en Linux. En macOS, si queda una carpeta
`.Colonia-<versión>.update` junto a `Colonia.app`, es una versión descargada que nunca se puso en su lugar; Colonia la borra la
próxima vez que arranca.

## macOS le pide a “node” acceso a Documentos

El core corre como `node`, la copia de Node que viene con Colonia. La primera vez que lee un proyecto en una carpeta que
macOS protege (Documentos, Escritorio, Descargas, iCloud Drive, un disco externo o de red), macOS pregunta si “node”
puede abrirla. Cuando el core arranca solo al iniciar sesión, esa ventana puede quedar detrás de otras, o aparecer sin
nadie frente al ordenador.

- Elige **Permitir**. Colonia lee el proyecto en cuanto respondes; no hace falta nada más.
- Mientras nadie responde, Colonia arranca y funciona como siempre. Los ajustes de ese proyecto dicen que su carpeta
  todavía no se abrió, y sus agentes no trabajan en su carpeta; tus otros proyectos siguen igual.
- Si elegiste **No permitir**, o la ventana ya no está: abre **Ajustes del Sistema › Privacidad y seguridad › Archivos
  y carpetas**, activa la carpeta debajo de “node” y reinicia Colonia (`colonia service restart`, o sal y abre la app de
  escritorio).
- Para que no pregunte, guarda los proyectos en una carpeta que macOS no protege, como `~/work/…`.

Antes de la 2.12.4 el core esperaba la respuesta para arrancar: la app de escritorio se quedaba en **Conectando con
Colonia** y `colonia status` no encontraba ningún core hasta que alguien respondía la ventana.

## El puerto ya está en uso

Un solo proceso puede escuchar en el `7440`. Si otro core ya lo tiene (un `pnpm dev` de antes, el core de la app de
escritorio, el servicio), un segundo core no arranca. `colonia service install` lo revisa antes y te lo dice:

```text
a core already answers on http://127.0.0.1:7440 and it is not the service's. Stop it first (it may be `pnpm dev` or the desktop app), then run install again.
```

Frena el otro, o dale a este core otro puerto con `COLONIA_PORT` (la terminal también sigue a `COLONIA_PORT` y a `core.env`).
La app de escritorio no se pelea por el puerto: si ya responde un core en el `7440`, usa ese.

## "Missing or bad token"

Cuando el core está expuesto (red local o Tailscale) tiene un token, y cada petición lo necesita, o la llave de un
dispositivo vinculado. El comando `colonia` y la app de escritorio en la misma máquina lo leen solos de `<home>/core.env`.
Si ves `Colonia · unauthorized` con `missing or bad token`:

- Estás usando otra carpeta que la del core: revisa `COLONIA_HOME`, o pasa `COLONIA_TOKEN` a mano.
- Estás en otra máquina: no copies el token, vincula (`colonia pair` en el servidor). Un navegador muestra **Vincula este
  dispositivo**.
- El dispositivo fue revocado: vincúlalo de nuevo.

Dos más con los que te puedes cruzar si cambias el acceso a mano:

- El core no arranca con `refusing to listen on 0.0.0.0 without COLONIA_TOKEN`: un `COLONIA_HOST` que no sea loopback siempre
  necesita token. `colonia expose lan` te crea uno.
- `a request through a proxy needs COLONIA_TOKEN on the core`: algo (como `tailscale serve`) le reenvía peticiones a un core
  sin token. `colonia expose tailscale` crea uno.

## Un cambio de acceso no se aplicó

El core lee `core.env` solo al arrancar. Después de `colonia expose`, ejecuta `colonia service restart` (el panel reinicia su
propio core cuando puede, o te dice **Guardado: se aplica cuando el core vuelva a arrancar**). `colonia status` muestra
`Restart needed` mientras el acceso guardado no coincida con el que está corriendo.

`colonia expose status` también te dice si una variable de entorno está pisando el archivo (por ejemplo `the environment
overrides: COLONIA_HOST`): las variables del proceso siempre ganan.

## Un código de vinculación no funciona

| Lo que ves | Por qué, y qué hacer |
|---|---|
| "Ese código es incorrecto o venció" | Los códigos duran 10 minutos y sirven una vez. Reiniciar el core también los anula. Pide uno nuevo. |
| "Demasiados códigos incorrectos" | Cinco códigos mal pausan la vinculación por cinco minutos. Espera y pide un código nuevo. |
| "Tu teléfono todavía no llega a este core" | El core solo escucha en su propio ordenador. Exponlo (red local o Tailscale), reinícialo y vincula de nuevo. |
| El otro dispositivo no conecta para nada | No está en la misma red (red local) o en tu tailnet (Tailscale), o la dirección está mal. Prueba la dirección en su navegador. |

## Un canal no responde

```bash
colonia channels          # el estado de cada canal y su último error
colonia channels outbox   # lo último que se mandó: queued, sending, sent, uncertain o failed, con el error
colonia pairing           # desconocidos esperando tu aprobación
```

- **Un desconocido no recibe respuesta**: por defecto, una persona nueva recibe un código de vinculación y te espera.
  Apruébala con `colonia pairing ok <code>` (o `colonia pairing me <code>` si eres tú desde otra dirección), o díselo a tu
  secretaria.
- **Tu propio mensaje parece no llegar a ningún lado**: por defecto, lo que escribes en un canal va al chat Home, así
  que la respuesta también está ahí.
- **Una persona está bloqueada**: las personas bloqueadas no reciben respuesta. Revisa `colonia contacts`.
- **Un envío quedó `uncertain`**: el core se cortó mientras mandaba, así que no puede saber si llegó. No se manda dos
  veces.
- **Dos Colonia contestan el mismo bot**: no corras Colonia v1 y v2 con el mismo bot. Por eso instalar v2 frena el daemon de v1.

Más en [Canales](/es/channels/overview/).

## Errores de modelos

```bash
colonia models            # cada motor, y "(not available)" con el motivo cuando no se puede usar
colonia models --refresh  # les vuelve a preguntar a los motores
colonia models config     # el predeterminado, la cadena del router y sus reglas
```

- **Un motor no está disponible**: casi siempre falta una clave o un inicio de sesión. Cárgalo en **Configuración ›
  Motores y modelos**.
- **El router no pasó al siguiente**: pasa al próximo modelo de la cadena solo cuando un modelo falla **antes de que
  corra alguna herramienta** en ese turno.
- **Un modelo tarda mucho en empezar a responder**: el core espera 45 segundos el primer byte (`COLONIA_LLM_TIMEOUT_MS`).

Más en [Modelos](/es/concepts/models/).

## Falla un servidor MCP

```bash
colonia mcps                    # cada servidor, su estado (ready, needs-approval, error…) y su error
colonia mcp check <server>      # una prueba de conexión: OK o Failed, el tiempo y la cantidad de herramientas
colonia mcp tools <server>      # lo que ofrece
```

<Terminal command="colonia mcp check notes">{`notes: Failed · 3012 ms · 0 tools
connect ECONNREFUSED 127.0.0.1:3000`}</Terminal>

- **needs-approval**: un servidor del `.apc/mcps.json` de un proyecto solo corre cuando confías en esa definición
  exacta: `colonia mcps trust <project> <server>`.
- **needs-sign-in**: pidió que inicies sesión en tu navegador y te espera; Colonia no lo vuelve a arrancar solo. Pulsa
  **Iniciar sesión** en **Recursos › MCP**, o ejecuta `colonia mcp signin <server>`.
- **Falta una clave**: los servidores MCP reciben sus secretos por referencia; cárgalos en **Recursos › Variables**.
- **Ambiguous server**: el mismo nombre existe global y en un proyecto. Suma `--project <id>` y `--scope`.

Más en [Servidores MCP](/es/extend/mcp/).

## El navegador necesita la app de escritorio

Los agentes manejan el navegador que presta la app de escritorio. Sin la app, el core usa su propio Chrome sin
ventana, que no te puede pasar el control y nunca usa tus sesiones iniciadas. Errores que puedes ver:

- `no connected node offers "browser" (open the Colonia desktop app)`: abre la app de escritorio en el ordenador donde corre
  el core, o una conectada a él por SSH. Una app conectada **por dirección** todavía no presta su navegador.
- `no Chrome, Chromium or Edge on this machine`: instala uno para el navegador sin ventana, o apunta `COLONIA_CHROME` a él.
  `COLONIA_HEADLESS=off` lo apaga.

Para leer páginas y buscar, los agentes también tienen `web_read` y `web_search`, que no necesitan navegador. Más en
[Navegador](/es/office/browser/).

## Colonia v1 y v2 a la vez

No se pisan:

| | Colonia v1 | Colonia v2 |
|---|---|---|
| Puerto | `7430` | `7440` |
| Datos | `~/.colonia` | `~/.colonia/v2` |

v2 nunca escribe los archivos de v1. Instalar v2 con el script frena el daemon de v1 y saca su comando `colonia`, porque
los dos contestarían en los mismos canales; los archivos de v1 quedan para que los importes con `colonia import-v1` o con
la configuración inicial (solo lee v1). `colonia daemon` es una costumbre de v1: en v2 te explica los comandos `colonia service`.

## Empezar de cero sin perder nada

Para probar algo arriesgado, arranca un segundo core con su propia carpeta, su propio puerto y los secretos en un
archivo, así nada toca tus datos reales ni tu Llavero:

```bash
# Desde el código
COLONIA_HOME=~/work/colonia-scratch COLONIA_PORT=7460 COLONIA_SECRETS=file pnpm dev

# Desde un paquete instalado
COLONIA_HOME=~/work/colonia-scratch COLONIA_PORT=7460 COLONIA_SECRETS=file \
  ~/.colonia/v2/app/current/node/bin/node ~/.colonia/v2/app/current/apps/core/src/main.ts
```

Después apunta la terminal a ese core:

```bash
COLONIA_HOME=~/work/colonia-scratch COLONIA_URL=http://127.0.0.1:7460 colonia status
```

Un core con su propio `COLONIA_HOME` tampoco toca las skills de Claude Code, Codex y Cursor. Cuando termines, borra la
carpeta de prueba.

<Aside type="caution">
No borres `~/.colonia/v2` para "resetear" Colonia: ahí están todos los agentes, chats, tareas y notas, y en un servidor también
la app instalada. Mueve las cosas a un lado, y solo con el core frenado.
</Aside>
